Local versions and branches

Save and switch

The Git panel reads the current repository, branch, commits and nonignored changes through the Agent Git API. Save commits the current changes locally. Switching branches first commits pending changes, then switches to an available local branch. A branch occupied by another worktree is unavailable. Active AI turns must finish or be stopped first.

These operations use the actual Git repository and do not push to GitHub. Source ZIPs contain no .git directory; first installation initializes version history after your storage choice. The version panel reads only this application repository, never a parent repository.

Name and load historical versions

Open the top-right version panel and select a committed version. Give it a custom Version name and choose Save name. Names can be changed again; empty text clears the alias. The SHA and original commit subject remain visible. Names are stored locally in the repository common Git directory and survive refresh/restart, but are not published by a push or included in source ZIPs.

Choose Switch version to load the selected commit in detached HEAD. This preserves named branch tips; pending work is first saved as a local commit. Saving work while detached retains it under refs/saplingagent/saved/<sha>, visible in version history. Select your application branch (release by default) under Branches to return. Source checkout does not restore private conversations or credentials, and source saves always exclude known private/runtime artifacts. If an old version lacks this panel, run git switch release from the project Terminal and restart the services.

Backend source or dependency changes require a service restart. This control only checks out source and refreshes the page. No GitHub push occurs.

Refresh and recovery

The footer displays branch/version and compares source fingerprints every five seconds and when visibility resumes. New source changes show a refresh button instead of automatically reloading the page. Frontend refresh does not reload a running backend process.

Git source history and optional app-builder originals are distinct from user conversations and credentials. Do not reset private data as part of a source rollback. Arbitrary shell side effects cannot be guaranteed reversible.

First-install Git storage

Customer downloads and source packaging default to release. Installation asks for: local-only Git history (no remote), your own existing repository URL (origin), or following the author release (upstream). There are only three choices: 1 Local reset (explicit number required), 2 My own remote, and 3 Follow author release. Choice 1 prints a reset notice, erases ALL existing root Git metadata (commits, branches, tags, aliases, index and config), and initializes empty main with zero commits and no remotes. Application files/data/credentials remain in place. The page shows main and No commits yet; Save version explicitly creates the first local record. Enter does not choose local automatically. Reinstall with a saved choice keeps later history; explicit local setup resets again. Choice 2 explicitly adds or updates origin to your supplied URL. Downloads default to release source. Local setup always starts empty main; own/follow use the configured initial branch.

Menu 5, Git / storage setup, or bash Saplingagent.sh git changes the choice. Stop the running application first. The saved choice lives in local .git/config; reinstall/repair preserves your selected branch/version. A linked development worktree retains its shared configuration. No global Git settings, automatic pull/push, hosted repository creation or PR. Local reset also removes custom origin/upstream/mirror links and all previous local Git records. Choice 2 retains unrelated non-author remotes. An explicit branch setting can select another branch; pending changes must be saved before switching. Storage submenu choices 4 and 0 are removed; the main menu still offers Diagnostics and Quit. Older saved keep-existing configurations remain valid on reinstall.

Create your own remote repository first and enter an HTTPS/SSH URL without tokens/passwords. Follow mode fetches author history and anchors the delivered source to its recorded commit; raw ZIPs must match upstream history. An unidentifiable/edited ZIP can use local/own storage or a Git clone. Fetch failure can be retried. Install / update updates dependencies, not source; review git fetch upstream and explicitly merge reviewed changes with git merge upstream/release. Resolve conflicts and review recipient goal/task records before restart. Adding follow mode to independent history may require a deliberate merge with --allow-unrelated-histories; setup does not rewrite existing history. Fast-forward-only pull stops on diverged history. Full Access is unchanged.

Unattended first setup: SAPLING_GIT_MODE=local|own|upstream, own remote in SAPLING_GIT_REMOTE, optional initial branch in SAPLING_GIT_BRANCH. Mac version history requires Git (Apple Command Line Tools if missing); Windows Git Bash supplies it. Source ZIPs contain no .git metadata; the installer initializes it after your choice.
