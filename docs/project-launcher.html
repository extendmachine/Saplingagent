Your project, your launcher

Kernel0.9.4 · schema3/layout1. Download the release-branch source or use the one-line installer for this version. The complete setup website and platform implementations live under kernel/.

  1. Run bash Saplingagent.sh in the complete source folder (macOS Terminal or Windows Git Bash). The script detects OS/architecture, installs project-local Node and kernel dependencies, and opens the setup page. Application dependencies are installed later.
  2. Set a project name, folder name and optional image. Uploaded PNG/JPEG/WebP images up to4MiB are cropped to a256×256PNG. Names support Unicode/spaces but reject nonportable filename characters. Save a Codex, OpenCode or Claude API/account scheme. Saving does not verify quota or send a prompt.
  3. Finish and save all project/AI changes, then choose Save settings & restart. Wait for the helper to close owned processes, apply the folder name and restart services. Existing destinations are never replaced; development worktrees remain in place. If another program holds the folder, close it and retry.
  4. After restart readiness, choose Export app. The browser shows compilation progress. A pinned, checksum-verified Go compiler is downloaded into .runtime; caches stay in .cache. macOS builds a named .app and Windows builds a named .exe locally, including the uploaded icon. Keep the whole folder; the launcher contains no app source, account or fixed developer path.
  5. Double-click the launcher to reopen the project. The native bootstrap starts the project-local management process and exits. Management reuses this folder's existing instance or starts its runtime, then opens the actual port. Use the management page to open, restart, stop, configure or rebuild this app.

Rebuilding safely

ChangeOperation
FrontendRebuild application pages
BackendRestart app
Name, icon or native sourceRebuild app & launcher

Native executables with unchanged source/name/icon are reused. Changed launchers are compiled and verified in same-volume staging before replacing the previous output. Success keeps one visible launcher and removes the superseded named output; failure preserves the previous usable output where replacement has not completed. A Windows lock, disk error or permission problem is reported explicitly; no universal I/O guarantee or silent data rollback. Close the native launcher and retry. A receipt records the locally compiled platform/architecture/time under .runtime/launcher.json.

Isolation and lifecycle

Two complete folders may install/configure/run independently. Setup uses an OS-assigned port, and application startup advances occupied ports, including bounded internal bind-race retries. Root plus runtime instance ID identifies the app; copying another folder's discovery does not authorize stopping it. Stop app drains active operations, then stops only owned services. Closing a browser tab does not stop the app. Closing setup is separate from stopping the app.

Recovery and commands

bash Saplingagent.sh configure --no-open
bash Saplingagent.sh install --repair
bash Saplingagent.sh doctor
SAPLING_LEGACY_MENU=1 bash Saplingagent.sh

The first command prints a management URL when browser opening fails. Dependency repair starts with kernel dependencies; use the web build to repair application dependencies. The legacy menu and explicit command actions remain fallback tools. No global Go/Node/npm installation, sudo or customer credential copy is required. Credentials and source remain editable with existing Full Access.

Platform limits

Targets: macOS Intel/Apple Silicon and native Windows10/11 x64/ARM64. Windows initially needs Git Bash for the .sh script; daily native launching does not require opening a terminal. Customer compilation uses the detected local architecture. Cross-compilation checks do not establish Windows installation/icon/rename/replacement acceptance. A locally built/ad-hoc-signed Mac launcher is not a Developer ID-notarized commercial app. Model access, provider quotas and networks require the customer's own account.

Finish edits, save, wait for restart, then export

Save the project name, desired folder and icon without moving the folder. Finish and save the AI account/API settings. Choose Save settings & restart, then wait for the page to confirm the restart before selecting Export app.

A private temporary system helper outside the project closes owned processes, waits for executable/log handles to be released, moves the folder and resumes from its actual path. Application dependencies/pages and services are prepared before readiness is confirmed. The helper removes only its own temporary files. Permanent helper source, logs and receipts stay with the complete project. Export does not rename.

Existing destinations and unrelated processes are preserved. A failure reports the actual folder and saved status for correction; it never automatically rolls back data or replaces a conversation. Existing Codex sessions retain their IDs and use verified local rollout recovery when required. Windows lock and real-account acceptance remain separate.
