Saplingagent macOS installation and setup

Kernel 0.9.5: this guide describes the current source workflow. The installer downloads the actual published release commit; main development changes reach recipients only after release promotion.

Install and configure

Use macOS Terminal on Intel or Apple Silicon. Node, dependencies and source stay in the project. Installation neither initializes Git nor deletes an existing customer repository.

bash -o pipefail -c 'curl -fsSL https://raw.githubusercontent.com/extendmachine/Saplingagent/release/install.sh | bash'

Alternatively extract the complete source and run bash Saplingagent.sh inside it.

  1. The script detects the device and installs the minimal kernel. Short-lived project process A copies the complete configuration bundle and an independent Node executable to a visible, session-owned sibling directory (../sapling-config-*), starts B there, then exits.
  2. Save your project name, target folder and icon in the web page. Then save your Codex account or Codex/OpenCode/Claude API scheme, including custom API URLs. Credentials stay in the project; Claude supports API credentials, not subscription login imports.
  3. Choose Save & build app. B stops owned services, waits for exit, applies the folder name and compiles the native launcher into the project. The configuration URL stays available. An existing destination is never overwritten.
  4. Wait for build completion, then choose Finish setup. B starts project-local A with its temporary-folder receipt, then exits. A waits for B exit before removing that verified temporary bundle.
  5. Open the project’s .app or .exe. It checks and installs missing or changed dependencies, then opens the project. Unchanged dependencies are reused. Daily Windows .exe startup does not need Git Bash.

Use the Dock to stop the project

The macOS app stays in the Dock as an ordinary application. Click its icon to reopen the project. Choose Quit from its menu or press Command-Q to stop this project’s existing services and exit. Closing the browser alone leaves the backend running. If shutdown fails, the app stays open with an error so you can check logs/project-launcher/ and retry.

After updating an existing installation, open configuration and choose Save & build app once to rebuild an older exported .app. Configuration waits for the native app and its startup helper to exit before renaming the project or replacing the app. The browser interface, service cluster and AI permissions remain unchanged.

Change settings and recover

Run bash Saplingagent.sh configure again. Save and build after changes, then finish setup. A successful build replaces the previous output; a failed build preserves it. Keep the launcher with its complete project folder. Closing a browser tab alone does not stop configuration.

If the browser does not open, use bash Saplingagent.sh configure --no-open and visit the printed address. Use bash Saplingagent.sh install --repair for missing installation files. Build failure preserves saved settings at the actual current folder; fix the issue and retry. Release files held by other software first. Logs are in logs/project-launcher/. Do not manually delete an active configuration temporary folder.

Installation/build may download pinned tools and locked dependencies, without sending a model prompt. Provider authentication, quota and model compatibility require separate verification. Native Windows installation, file locking, icons and rebuild behavior still require hardware acceptance.
