Saplingagent · Platform maintenance

Your application.
A separately maintained kernel.

Receive shared platform improvements while keeping your application's code, Git history and private records. Original kernel baseline: 0.90.

Updates can invalidate existing functionality

A compatible manifest cannot guarantee that custom imports, dependencies, services or external integrations still work. Preview changes, stop the app and back up important business data before applying. An owned-source backup is created, but source recovery cannot undo business data changes. Updates are optional and require explicit compatibility-risk acknowledgement.

Membership defines the update package. Existing current-user Full Access remains unchanged. You may edit core source; changes can conflict with later updates. Do not regenerate a recipient manifest just to conceal those differences.

Open independent management

bash Saplingagent.sh kernel

Or choose 6. Kernel management from the launcher, available with local Git, your own repository or follow-release storage. The kernel has no daemon, additional port or model request. It downloads the official public release at one immutable commit; it never runs Git checkout/merge, changes remotes or uploads local content.

CommandResult
kernel statusInstalled version, original baseline and local backup IDs.
kernel checkDownload a staged preview, validate hashes/compatibility and list conflicts. Application source stays unchanged.
kernel updatePreview, acknowledge risk, back up and apply owned source while the app is stopped.
kernel restore <backup-id>Explicitly recover recorded source; refuse unrelated later edits.

Commands are passed after bash Saplingagent.sh. Noninteractive update additionally requires --accept-risk; using it deliberately accepts the same compatibility warning.

Update, repair, verify

  1. Run bash Saplingagent.sh kernel check. Resolve listed core conflicts deliberately. Unchanged upstream files with local customizations are preserved.
  2. Back up important application data and stop this app using Control+C in its startup terminal. Apply/restore refuse a live owned runtime or installation.
  3. Run bash Saplingagent.sh kernel update. Review the preview and type UPDATE to acknowledge the warning. Keep the reported backup ID.
  4. Run bash Saplingagent.sh install --repair to install the applied dependency declarations without merging application source.
  5. Start the app normally; verify health, your existing application and an existing conversation. The footer displays the installed kernel version separately from Git.

Source applied is not runtime-ready. Update does not automatically start the app, run a model or migrate your data. Ordinary application changes still use the in-page Restart app control.

If the new kernel fails

bash Saplingagent.sh kernel status
bash Saplingagent.sh kernel restore <backup-id>
bash Saplingagent.sh install --repair

Stop the app first, restore explicitly, repair old dependencies, then start and verify. Original bytes/modes and a journal stay under .runtime/kernel/backups/. Partial application is recorded; there is no automatic rollback. Recovery checks every target before writing and refuses source edited after the update.

If the new launcher cannot run, use the previous project Node executable directly with the saved independent helper:

<project-node-executable> .runtime/kernel/recover.mjs <backup-id>

The previous updater copies this self-contained helper before replacing source. It needs no installed npm dependencies. Keep the old Node runtime if a new release changes its version. A failed or interrupted operation can leave .runtime/kernel-operation.lock; inspect its PID/owner and confirm that operation is stopped before removing only that stale lock manually. Backups are retained locally; manage their retention yourself after verification.

Publishing and limits

The maintainer generates and checks kernel/manifest.json with node kernel/build-manifest.mjs --maintainer and --check. A new kernel becomes available only after those checked files are deliberately published to release. Older releases without the manifest report KERNEL_UNAVAILABLE; do not interpret that as a completed update.

Unsupported application API changes, a Node runtime below the minimum, invalid paths, hash mismatches, changed previews and automatic downgrades are refused. Public GitHub access is required; network or rate-limit errors leave source unchanged. Hashes validate a commit-pinned download, not a separate publisher signature. Native Windows update/recovery still requires hardware acceptance.
