Saplingagent concept and solution

Saplingagent is a seed that can be grown locally by users as applications. The React web page provides a stable chat entrance and an evolutionary work canvas, and the local Agent can complete data query, function construction, tool extension and version recovery.

I. Eight concepts and solutions

The user's original text has been saved in the root FINAL_GOAL.md; the following table is the corresponding scheme, and the implementation proposal is not impersonated as a completed ability.

III. Fixed dialogue entrance and evolveable interface

The only stable basic interface is the chat entrance, which reuses the open source library. Other interfaces include canvas frame, function navigation, area assembler, business panel, result display and theme, which allow AI to modify its React source code and layout.

Recommended basic chat candidatesassistant-ui, the official document provides React chat components and self-back-end connections; canvas candidatesReact Flow, can carry custom nodes and interactive diagrams. Currently reserved assistant-ui 0.15.26; TASK-20261009-004 has removed React Flow, and the real Agent adaptation is still not connected.

Initially, four types of dynamic areas are recommended: functional navigation, task operation, result preview, and context details. They are the initial work content, not the four permanent slots. Agent can be added, deleted, split and adjusted. The chat area is independent of dynamic module loading; messages can still be sent and restored when the dynamic area construction fails.

Processing at different levels: layout changes update coordinates, size, grouping and viewport; component changes generate and compile React modules; function changes synchronize front-end, back-end, interface and data requirements. The component stable ID retains the user's editing status, and the layout rollback does not roll back the business data.

Components interact with props, public events and shared contracts, style limits the scope, and sets an error boundary for each area. Any generated code that requires permission isolation is placed in an independent source iframe or restricted back-end process; the error boundary only handles rendering failures and cannot replace permission isolation.

IV. How does AI generate MCP and modify applications?

Minimum read, write candidate, check, build, preview and recovery capabilities must be provided in the seed first. In this way, Agent can create the first new tool without relying on self-generated MCP that does not exist yet to complete the startup.

Users put forward their needs

→ Agent reads local rules, goals, existing functions, layouts and preferences

→ Query the required official information and record the source

→ Form a declaration of modification scope, interface and candidate function

→ Generate front-end, back-end or MCP server in the candidate work area

→ Check the functional behavior of path, contract, type, construction and isolation

→ Preview the candidate, enable or keep the version pending acceptance according to the current authorization

→ Save the version and the basis, and then correct or restore

MCP is a tool connection protocol. The real source code writing, compilation and process execution are implemented by the local back-end. The original tool can be reused first when it completes the requirements; when new capabilities are needed, the app-builder generates an independent MCP server, and it is registered by mcp-runtime after verification. GovernmentMCP server construction documentDefine tools, resources, prompts to connect with the host.

Each modification carries app_id, feature_id, target file scope, basis, expected basic version, required capabilities and verification records. The write path is resolved to the root directory of the current application and cannot escape from the application through symbolic links or relative paths; the generation tool cannot bypass the host permission. The authorized general modifications continue to be implemented, involving main synchronization, data migration or external release, which still abides by the existing project rules.

The local launcher and recovery facility belong to the operating infrastructure; functional construction tasks are operated through their public interfaces and do not arbitrarily cover their own recovery entrance. Follow the clear base version process when upgrading the base in the future. This does not solidify other interface components.

V. How to verify long-term personalization

At the same time, keep clear preferences, temporary requirements and behavioral speculations. Each preference includes the applicable user and scenario, message or event source, recent correction, status and version. The priority is the current clear requirements, user fixed settings, confirmed preferences, behavior speculation, and default layout.

Obviously, the user's requirements can be implemented directly; the candidate hypothesis is formed first according to the adjustment of behavior speculation. Observe the operation steps, time-consuming, success rate, cancellation and clear evaluation of tasks of the same type. Neither the self-evaluation of the large model nor the single click can prove that the layout is better; the difficulty of the task, the delay of the model and the time of page operation should be recorded separately. If the evidence is insufficient, continue to observe, and if the effect deteriorates, correct or restore.

Component changes, layout changes and user feedback are all related to the version; keep the original evidence summary and source identification to reduce subsequent repeated inquiries. New applications initialize empty preferences. When copying mature applications, choose whether to inherit the layout separately. The original customer identity and memory cannot be copied by default.

VI. Minimum start-up entrance and distribution

In the future, the entrance will locate its own directory, check the seed version, bring in the complete rules and entrance files, establish the local state and environment, select the local port, start the back-end and React web page, and then open the browser. Repeated startup to restore existing applications without overwriting existing data and modifications.

New functions default to build modules of the same name in front/features/ and backend/features/ of the current application; when users want to apply independently, they copy the base in the new directory and initialize the new app_id. The two modes reuse the same startup entrance to avoid unintentionally copying the entire customer information of each function.

At present, the cloud is not built, and the most implementable is the offline seed compression package that contains the startup entrance and seed content. If you are required to copy only one file, you can embed the seed source code, data and rules into the self-unpacking entrance; the volume will increase. A very small online boot script must have an available download source, a fixed version and a hash, and it cannot be assumed that the future cloud already exists.

Carry the list and version of rules in the startup entrance, and do not pull the "latest version" rules to cover the customer's specifications by default. New projects rebuild FINAL_GOAL, TODO and AI_TASKS; with empty credentials skeleton, cannot carry the developer's real general ledger. Code and packets do not mean that all runtime has been packaged. Whether the operating system, Node is preset, model endpoints and dependency reconstruction methods need to be determined before implementation.
