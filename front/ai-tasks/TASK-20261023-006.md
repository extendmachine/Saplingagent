## Scope and contract

Only front/chat source/tests/README and this handoff were modified. Root service CONTRACT/SERVICE/DEPLOY and shared interface/human documentation are coordinator-owned. No changes to application features, kernel, SDKs, dependencies, accounts, real conversations, customer projects, root task indexes, release or tags.

The UI now exposes engine/provider/model selection for existing conversations. The selection is staged and applied explicitly through POST /api/sessions/:id/engine {engine,providerId,modelId,expectedEngineRevision}. The response must contain the same session ID, complete messages, matching binding and valid revision. Codex remains its configured project-default model; no unsupported Codex model catalog was introduced. OpenCode/Claude use the existing actual catalogs. New conversations retain direct selection before the first message.

Successful changes keep logical session/messages/title and composer text/attachment state; there is no composer reset or automatic chat POST. Pending submissions prevent changes until attachment preparation/send finishes. Running/loading/restarting/mutation states block new changes; the hook guards its public operations independently from button state. Existing conversation navigation can still leave an active response, as before, but is blocked during the short engine mutation.

Snapshots restore engineRevision(default0 for legacy), handoff and summary binding. The same selection is a no-op. Real changes clear stale tools/approval/context/retry. Pending handoff is a status note, not a fabricated user message: history is passed on the next explicit user send. Chat requests on an existing session include engineRevision. Old retry input is not forwarded to another engine. After reload, the persisted handoff.throughMessageId separates historical messages from retryable requests of the current binding.

Epoch and list guards reject pre-switch delayed snapshots/history. Rejected, malformed or failed responses leave the previous visible selection/content and report an error. An uncertain network outcome may require reloading the conversation to obtain the server's current revision; there is no silent model resend or forced rollback.
