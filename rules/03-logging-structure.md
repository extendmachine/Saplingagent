# 03. 独立日志目录与按服务划分

## 目标

每个项目必须有独立的 `logs/` 文件夹，用于集中记录各微服务日志。日志按服务划分子目录，一个微服务一个文件夹，一天一个日志文件，保留 30 天，方便检索、清理和排查问题。

## 推荐目录结构

```text
logs/
├── service-a/
│   └── service-a-YYYY-MM-DD.log
├── service-b/
│   └── service-b-YYYY-MM-DD.log
└── service-c/
    └── service-c-YYYY-MM-DD.log
```

## AI 执行规则

1. 每个服务只能写入自己的日志子目录。
2. 日志文件命名建议包含服务名和日期，例如 `service-a-2026-07-10.log`。
3. 每个服务每天只生成当天对应的日志文件，不混写到其他日期文件。
4. 日志默认保留 30 天，超过 30 天的日志应自动或定期清理。
5. 新增服务时，应同步建立对应日志目录规划。
6. `logs/` 目录一般应加入 `.gitignore`，日志文件不入库。
7. 如需保留目录结构，可使用 `.gitkeep`，但不要提交真实日志内容。
8. 新项目或新增服务按下方“日志方案填写格式”记录日志规划，最终内容直接写入该服务的 `SERVICE.md`。
9. 规范源目录预建 `logs/README.md` 作为安全空骨架并随整包复制；其中不得出现真实日志文件，目标项目产生的真实日志继续保持 Git 忽略。

## 日志方案填写格式

在微服务 `SERVICE.md` 中直接维护以下内容，不创建单独模板文件：

```markdown
## 日志

- 服务：`<SERVICE_NAME>`
- 日志目录：`logs/<service-name>/`
- 文件名称：`<service-name>-YYYY-MM-DD.log`
- 普通日志保留：30 天
- 清理方式：<启动时 / 定时任务 / 人工维护>
- 日志等级：<DEBUG / INFO / WARN / ERROR>
- 错误关联字段：<request_id / task_id / trace_id>
```

## 禁止事项

- 禁止多个服务混写同一个日志文件。
- 禁止长期堆积超过 30 天的普通运行日志。
- 禁止把真实运行日志提交到 git。
- 禁止把敏感信息写入日志。
