# 04. Git 分支、测试确认与 main 同步

## 目标

Git 分支必须按微服务和特性划分。AI 负责创建、维护、提交和整理全部微服务分支与特性分支；用户主要审阅和使用 `main`，并在分支完成后负责人工测试与确认。

任何进入 `main` 的内容都必须能追溯到来源分支和用户实际测试过的提交版本，防止测试版本与合并版本不一致。

多个 AI 或多个对话并行工作时，还必须遵守 `rules/14-multi-ai-task-worktree-handoff.md`，一个任务使用一个独立分支和一个独立 Worktree。

本文件的提交、测试版本和 main 同步流程适用于 Git 项目的修改任务。只读任务和非 Git 文档任务按规则 09 交付，不为流程创建虚构分支或提交。

## 分支类型与命名

1. `main`：项目最新、最全、经过人工确认的稳定代码。
2. 微服务长期分支：推荐使用 `service/<service-name>`，用于归集该微服务已经完成但尚未进入 `main` 的修改。
3. 特性分支：推荐使用 `feature/<service-name>/<feature-name>`，用于单项功能开发。
4. 修复分支：推荐使用 `fix/<service-name>/<issue-name>`，用于单项问题修复。
5. 项目已有其他命名规则时可以沿用，但分支名称必须能识别所属微服务和修改内容。
6. 新建微服务时，AI 必须同步创建或规划对应的微服务分支。
7. 无微服务归属的规范、文档和协调任务可使用 `chore/project/<task-name>` 等可识别的项目级分支；只维护对应项目级内容，不借此混入多个服务的业务改动。

## AI 负责的分支管理

1. 修改前识别涉及的微服务，并切换或创建对应分支。
2. 开发内容完成后，先维护该服务的说明、接口、部署文档和任务记录，再提交到对应分支；根进度按规则 14 由协调者汇总。
3. 提交前执行文档筛选、敏感信息检查和修改范围检查。
4. AI 负责记录各特性分支的用途、状态、最新提交和所属微服务，用户不需要日常管理这些分支。
5. 同一特性分支不得混入其他微服务或无关任务的修改。
6. 分支进入待测试状态后，AI 不得继续修改该待测提交；如需修改，必须产生新的提交并重新通知用户测试。
7. 已确认并同步到 `main` 的特性分支，由 AI 按项目需要保留、归档或清理；执行删除前仍需遵守项目的分支保护要求。
8. 项目配置了远程仓库时，AI 应将完成的待测分支推送到对应远程分支；没有远程仓库时，保留在本地并明确说明。

## 分支管理清单

协调者必须在权威 `TODO.md` 中维护“Git 分支管理”区块，至少记录以下信息；单任务由执行 AI 兼任协调者：

1. 分支名称。
2. 所属微服务和功能。
3. 最近已记录的实际提交编号，以及当前冻结的待测提交编号（如有）；不要求记录文件所在提交包含它自身的 SHA。
4. 当前状态：开发中、实现及自检完成、待人工测试、测试未通过、测试通过待同步、已同步 `main` 或已归档。
5. 对应的 `main` 合并提交编号；尚未同步时填写“无”。
6. 最后更新时间和下一步动作。
7. 执行 AI、任务编号和 Worktree 位置。

## 完成后的交付信息

AI 完成分支内容后，必须向用户提供以下信息，并按下方冻结规则汇总到权威 `TODO.md`：

1. 来源分支名称。
2. 待测试提交的完整或可唯一识别的提交编号。
3. 本次修改内容和涉及的微服务。
4. 用户需要执行的测试步骤和预期结果。
5. 尚未验证的风险或注意事项。
6. 交付人工验收时状态标记为“待人工测试”；可以说明实现及自检已完成，但不得声称人工验收通过或已进入 `main`。

## 冻结版本与记录提交

1. 先完成候选分支的实现、应随版本交付的文档和自检，再取得最终提交 SHA。该 SHA 是用户实际测试的冻结版本，必须在交付回执中给出。
2. 冻结后不为回填 SHA、人工结果或进度再次修改候选分支。先在交付回执记录，再由协调者写入未冻结的协调分支 `TODO.md`、`AI_TASKS.md`；需要时单一 AI 也可按规则 14 建立项目内协调 Worktree，自行兼任协调者。
3. 记录提交追踪的是明确指出的候选提交或合并提交，不要求回写记录提交自身的 SHA。待测版本、人工结果和 main 合并编号分开记录。
4. 协调记录需要进入 main 时，从协调分支创建独立的项目级文档交付分支并冻结其快照；仍须人工审阅确认该提交。实时协调分支继续记录任务，不把持续更新的索引直接作为冻结候选。
5. 本规则只区分记录位置，不豁免重测：候选分支在测试后发生任何提交变化，仍须重新测试确认；不得把文档或元数据提交悄悄附加到已批准版本。

## 用户测试与确认

1. 用户应针对 AI 指定的来源分支和提交编号进行测试。
2. 用户反馈测试通过后，AI 必须确认用户测试的提交仍是准备合并的提交。
3. 如果待合并分支在测试后新增、改写或变更了提交，原测试结果失效，必须重新测试并确认。
4. 测试未通过时，AI 继续在原特性分支或对应修复分支处理，不得把未通过内容同步到 `main`。
5. 用户只需给出测试结果和是否允许同步到 `main` 的确认，具体分支操作由 AI 负责。

## 同步到 main 的规则

1. 只有用户明确确认指定提交测试通过后，AI 才允许将其同步到 `main`。
2. 同步前先更新本地 `main`，检查来源分支与最新 `main` 的兼容情况；如果发生冲突或产生实际代码变化，解决后必须重新请用户测试。
3. 每次同步到 `main` 只能包含一个可独立审阅的微服务或特性范围。
4. 合并应保留清晰的来源记录。合并提交说明至少包含：

```text
Source-Branch: feature/service-name/feature-name
Tested-Commit: <用户实际测试通过的提交编号>
Validated-By: user
Agent: Codex / Claude-Code / other
Task-ID: TASK-YYYYMMDD-001
```

5. 推荐使用保留合并提交的方式同步，避免来源分支信息因压缩提交而丢失。
6. 同步完成后，AI 必须将 `main` 的合并提交编号、来源分支、已测试提交和同步时间交给协调者，写入未冻结协调分支的权威 `TODO.md`；不直接在 main 补交未审阅的记录修改。
7. 未获得用户确认时，AI 不得自行合并、变基后合并或推送到 `main`。
8. 项目配置了远程仓库时，AI 在本地同步完成并核对无误后，负责将 `main` 推送到远程；用户不需要手工处理特性分支。

## 多服务改动

一次任务涉及多个微服务时，必须按服务拆分：

1. 每个微服务使用自己的分支和提交。
2. 分别向用户提供测试版本。
3. 分别取得人工测试确认。
4. 分别同步到 `main`，每次保留各自的来源分支和已测试提交标记。

## 异常情况

1. 紧急修复也必须使用独立修复分支并保留来源标记，不允许直接在 `main` 开发。
2. 如果发现 `main` 含有未经测试的提交，应立即停止继续同步，在 `TODO.md` 记录情况并等待人工决定处理方式。
3. 如果来源分支已不存在，但仍需同步，AI 必须先恢复可追溯分支或明确对应提交，不得凭记忆合并。
