# Distribution release identity

TASK-20261017-001, 2026-10-17. `config/release.json` is the single public product-version declaration: `{schemaVersion:1,version:"0.9.2"}`. It describes the installed Saplingagent distribution, not customer Git history or the independently installed kernel. It contains no credentials, mutable task state or self-referencing commit hash. `contracts/release.mjs` validates and reads only its schema and version. Invalid/absent metadata is unavailable; never infer a product version from the kernel baseline or a branch name.

GET `/api/release` is documented by Agent/front contracts. Source ZIP `delivery.json` adds `releaseVersion` alongside the exact `sourceCommit`; filenames contain both. The Bash source downloader records the version from the pinned snapshot. Git reset/local mode does not remove this file. Kernel updates do not own `config/release.json`; older apps without the additive HTTP route show release unavailable while retaining chat/kernel/Git controls. A kernel-only update must not claim that the complete application distribution was upgraded.

Maintainer sequence: freeze and verify code first; choose the next unoccupied product version; update this declaration, release notes and affected docs; self-check the final committed source; integrate main; promote to release retaining showcases; run `node scripts/verify-release.mjs --ref release --main <frozen-main-sha> --version <version>`; create a new immutable tag only at the checked release SHA; rerun with `--tag v<version>`; package that exact SHA, audit delivery version/commit/hashes, then publish a GitHub Release for the same tag/assets. Verify remote refs and downloaded content. Never move an already public tag or describe a bare tag as a completed GitHub Release. Code, product, kernel, customer Git and package identities must be reported separately.
